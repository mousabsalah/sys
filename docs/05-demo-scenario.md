# 05 — سناريو العرض أمام المشرف / لجنة المناقشة

> **إلى الأستاذ المشرف**: هذا هو مسار الفحص المقترح الذي يمكنك تطبيقه على النظام (منطقيًا أولًا، ثم عمليًا بعد التنفيذ). خطوة ← عمل متوقَّع ← ماذا ترى إن كان النظام صحيحًا. (النطاق: v1 = الشاشات الـ8 **+ وحدة الامتحانات** باعتراف المشرف 2026-11-09.)
> التواريخ/الأرقام في الديمو أمثلة وهمية مقصودة — لا تُوثق كبيانات حقيقية.

## 5.1 تجهيز الديمو (قبل دخول اللجنة بـ 30 دقيقة)

| # | الخطوة | التحقق |

## 5.2 خطوات الفحص بالترتيب (المدة ≈ 15–20 دقيقة)

### الخطوة 1 — تسجيل الدخول كمدير النظام (`admin`)
- افتح `/login` → «تسجيل الدخول» (كروكي `photo_8`: شعار الجامعة + «الدور يتحدد من الحساب»).
- **المتوقَّع**: دخول ناجح → تحويل إلى «لوحة التحكم»؛ خطأ كلمة مرور → رسالة عربية عامة («بيانات الدخول غير صحيحة») — **ممنوع** كشف أيّ الحقل خطأ (username أم password).

### الخطوة 2 — لوحة التحكم (كروكي `photo_6`)
- **المتوقَّع**: 4 أرقام (القاعات المسجلة / محاضرات الفصل / حجوزات اليوم / قاعات متاحة الآن) + «آخر الحجوزات» + «تنبيهات التعارض» (صف «[قاعة] محجوزة مرتين» لو وُجد ازدواج مُتعمَّد في البيانات التجريبية).
- login بـ `dept-sci` ← **المتوقَّع**: نفس اللوحة لكن **محصورة بكلية العلوم فقط** (دفعاتها/شعبها/جداولها) — لا تتسرب دفعات الهندسة مثلًا؛ admin له فلتر «الكلية» اختياري أعلاه.
- **سؤال للجنة**: من أين تأتي الأرقام؟ → تجميع SQL/Go داخل transaction قراءة — لا حسابات في الواجهة.

### الخطوة 3 — البيانات الأساسية (كروكي `photo_2`)
- تبويب **القاعات** → ابحث «قاعة 12» → **أضف** «قاعة 12» سعة 45 متاحة → **المتوقَّع**: تظهر في الجدول.
- أضف قاعة بنفس الاسم → **المتوقَّع**: رفض عربي «اسم القاعة مستخدم من قبل» (unique).
- غيّر «السعة» لـ 0 أو سالبة → رفض (`capacity > 0`).
- أضف «معمل 3» تجهيزات «أجهزة حاسوب + جهاز عرض» — **المتوقَّع**: التبويبات الأربعة تعمل بنفس النمط (المقررات / الأعضاء / الدفعات).

### الخطوة 4 — إعداد الجدول + كشف التعارض (كروكي `photo_1`) — **أهم خطوة**
1. املأ: المقرر «هياكل البيانات»، العضو «د. أحمد عبد الله»، الدفعة «حاسبات 2024» (78 طالبًا)، القاعة «قاعة 12» (سعة 45) ← **صغير العدد**.
2. اليوم «السبت»، من 10:00 إلى 12:00 ← اضغط **«تحقق من التعارض»**.
3. **المتوقَّع في لوحة «نتيجة التحقق»**:
   - «السعة: [45] أقل من عدد الطلاب [78]» (hard) ← **الحفظ مرفوض**.
4. بدّل القاعة إلى «قاعة 1» (سعة 120) ← تحقق مرة أخرى ←
   - **«عضو هيئة التدريس: لا تعارض ✓»** (كما في الكروكي) ← احفظ عبر **«حفظ في الجدول»**.
5. **محاولة ازدواج متعمدة**: أنشئ محاضرة ثانية لنفس القاعة في نفس السبت 10:00–12:00 → تحقق ←
   - **«القاعة: تعارض، محجوزة في هذا الوقت»** ← مرفوض؛ ولو غيّرت العضو لنفس القاعة/الوقت يظهر نفس السبب (القاعة تحسم قبل العضو في تسلسل التحقق).
6. **عضو مشترك**: نفس المدرس في قاعة مختلفة في نفس السبت 10:00 ← **«عضو هيئة التدريس: تعارض»** ← مرفوض.

> للمشرف: هذا يثبت أن سلسلة التحققات السبعة تعمل **قبل** الكتابة، وأن رفض الكتابة لا يترك سطورًا يتيمة في D5/D9.

### الخطوة 5 — عرض الجداول ومرونة الفترات (كروكي `photo_7`)
- «عرض الجداول» ← حسب «الدفعة» ← «حاسبات 2024» ← **المتوقَّع**: شبكة السبت–الخميس بصفوف فترات برنامج الدفعة (صباحي: 08/10/12/14).
- بدّل إلى دفعة من البرنامج «مسائي» ← **المتوقَّع**: الصفوف تتغير (17/19/21…) — إثبات أن الفترات لكل برنامج وليست شبكة ثابتة.
- **سؤال دفاعي**: لو عدّلت فترات البرنامج غدًا، هل تتأثر المحاضرات المحفوظة؟ → **لا** — الجدول يخزّن `day/start/end` مباشرة؛ الفترات تقود العرض والخيارات فقط.

### الخطوة 6 — الحجوزات (كروكيا `photo_3` و`photo_4`)
- «حجز قاعة» ← قاعة «قاعة 7» ← التاريخ/من←إلى ← «ندوة اليوم المفتوح» ← **حالة القاعة في الوقت المحدد: متاحة** ← **تأكيد الحجز** ← **المتوقَّع**: يظهر في «حجوزات القاعة في اليوم نفسه».
- ثم «القاعات المتاحة» ← التاريخ/من←إلى/أقل سعة=50 ← **المتوقَّع**: كاردات المطابقة فقط → اضغط **احجز** على واحدة ← انتقال إلى نموذج الحجز بقيم مُعبّأة.
- حجز نفس القاعة/الوقت مرتين ← **المتوقَّع واحد منهما 200 والآخر 409** «القاعة محجوزة للتو» (transaction + FOR UPDATE).

### الخطوة 7 — الحارس الجامعي (سجل القفل)
- دخول `guard1` ← **المتوقَّع**: لا يرى «إعداد الجدول» ولا «البيانات الأساسية» ولا «التقارير» — فقط «القاعات الخالية الآن» و«قفل/فتح».
- اقفل قاعة خالية ← **المتوقَّع**: صف جديد في سجل القفل (وقت/حارس/قاعة/إجراء) ← افتحها.
- حاول قفل قاعة فيها محاضرة **أو امتحان** الآن ← **المتوقَّع**: رفض بأسباب («لا يمكن القفل — توجد محاضرة/امتحان/حجز حالي»).
- كـ `admin` افتح «سجل القفل» ← **المتوقَّع**: السجلات كلها ظاهرة؛ **لا يوجد زر حذف** (السجلات غير قابلة للتدمير).

### الخطوة 8 — حساب الدفعة (عرض فقط + الإشعارات)
- دخول `batch-cs2024` ← **المتوقَّع**: يرى جدول/امتحانات **مساري دفعته (دبلوم وبكلاريوس) فقط** — لا دفعة أخرى، ولا تحرير.
- بعد Step 4/6/8.5: يظهر وسم «جديد» على آخر تعديل (إضافة محاضرة / تعديل / **امتحانا**) مع وصفه ووقته — «جديد» = `created_at` بعد `last_login_at`.
- حاول افتح `/api/timetables?group_id=غير-دفعتك` أو `/api/exams?group_id=غير-دفعتك` ← **المتوقَّع**: 403 (سياسة لا واجهة تخفي فقط).

### الخطوة 8.5 — الامتحانات (الاعتماد الجديد)
1. كـ `admin` افتح «إعداد امتحان» ← اختر: المقرر «هياكل البيانات»، الشعبة «الأولى بكلاريوس»، القاعة «قاعة 1»، التاريخ «2026-12-15»، من 09:00 إلى 11:00، النوع «فاينل» ← **«تحقق من التعارض»** ← **المتوقَّع**: بلا تعارض (القاعة والمشعبة/التاريخ فاضيان) ← **«حفظ في جدول الامتحانات»**.
2. حاول حفظ امتحانًا ثانيًا لنفس الشعبة في نفس التاريخ ← **المتوقَّع**: رفض بـ«لا يمكن أكثر من امتحانيْن للشعبة في نفس اليوم» (R8) — أو «لمقرر واحد مرتين» (R6 الفرعي).
3. حاول حفظ امتحان في قاعة مستضيفة محاضرةً في نفس التاريخ/الفترة ← **المتوقَّع**: رفض بأسباب R7 («محاضرة في نفس القاعة والفترة»).
4. افتح «عرض جدول الامتحانات» ← حسب «الشعبة» ← «الأولى بكلاريوس» ← **المتوقَّع**: تواريخ الامتحانات وأعمدتها مرتبة زمنيًا؛ عنصر جديد موسوم «جديد» في كشف حساب الدفعة.

### الخطوة 9 — التقارير والتصدير (كروكي `photo_5`)
- «التقارير» ← النوع «استخدام القاعات» ← الفترة ← **إنشاء** ← **المتوقَّع**: مخطط أعمدة + جدول «القاعة | عدد المحاضرات | نسبة الاستخدام» ← **تصدير** ← ملف CSV يفتح في Excel.
- **سؤال دفاعي**: النسبة محسوبة من إيش؟ → (دقائق المحاضرات الفعلية + الحجوزات المؤكدة) ÷ (دقائق الفترات المتاحة للبرنامج × عدد الأيام) خلال الفترة المحددة — معادلتها موثقة في README التقرير.

## 5.4 أسئلة متوقعة من المشرف — مع أجوبة معتمدة

1. **«ليه Laravel مع Go؟ مكنش يكفي واحد؟»** — Laravel للتنسيق والأعمال (auth, RBAC, transactions, CRUD) بـ PHP السريع للتطوير؛ Go للمهام الحسابية (فحص التعارض الواسع + تجميع التقارير) بسرعة 40× تقريبًا؛ الفصل يعطي قابلية النشر المستقل واختبارات Go منفصلة.
2. **«ليه مش Microservices أو Event-Driven؟»** — حجم v1 لا يبرر تعقيد التنسيق (قرار فصلك نفسه عن Microservices: فصل 2-2-3). Modular Monolith + حدود وحدات صارمة تتيح الفصل لاحقًا بلا إعادة كتابة.
3. **«ازاي تمنع ازدواج الحجز لو ضغطوا الزر مرتين بسرعة؟»** — transaction + `SELECT … FOR UPDATE` على صف القاعة + Idempotency-Key من الواجهة؛ الخاسر في السباق يأخذ 409.
4. **«ليه الفترات لكل برنامج مش عالمية؟»** — جداول صباحية ومسائية مختلفة جذريًا (8× عمل vs 17×)؛ برنامج = مالك الفترات؛ الشبكة تُرسم من فترات برنامج الدفعة المعروضة.
5. **«ليه الجدول لا يرتبط بـ periods بـ FK؟»** — حماية البيانات التاريخية: تعديل فترة مستقبلية لا يمس محاضرة محفوظة في الماضي؛ FK هنا مكسر للتاريخ.
6. **«ليه لا يوجد إشعار push للدفعة؟»** — قرار مقصود: حساب عرض واحد لكل دفعة؛ الإشعار مكانه عند الدخول («جديد» مقابل آخر دخول) — يوفي بالمتطلب بلا بنية دفع/إشعارات ثالثة في v1.
7. **«ماذا يحدث لو تعطلت خدمة Go أثناء الديمو؟»** — Laravel يعرض «الخدمة الحسابية متاحة لاحقًا» مع HTTP 503 واضح؛ الحفظ اليدوي لا يتم بلا فحص ناجح (لا مخاطرة بجدول ملوث)؛ التقارير تُعرض «التجميع قيد المعالجة».
8. **«أين يبدأ الذكاء الاصطناعي في النظام؟»** — لا يوجد ذكاء في v1 ولا ندّعي امتلاكه؛ Urgent work = correctness أولاً؛ التوليد الآلي (CP-SAT) مرحلة معتمدة مستقبلية بواجهة «اقتراح» تمر بنفس تحقق P2.
9. **«كيف يثبت التطبيق أنه «لكل جامعة» وليس «جامعة واحدة»؟»** — كل القيم (البرامج/الفترات/الأيام/السعة/التجهيزات) بيانات وليست كودًا؛ جامعة جديدة = seeders جديدة فقط، صفر تعديل كود.
10. **«ما أكبر نقطة ضعف حاليًا؟»** — لا اختبار حمل (load) على خدمة Go؛ الخطة: k6 Script يضرب `/check` بـ 200 RPS قبل النشر على بيئة الجامعة.
11. **«ليه soft delete؟»** — الجداول التاريخية لاتُفقد بمجرد حذف قاعة obsoleted؛ التقارير السنوية تبقى صحيحة.
12. **«إيه اللي اتدفع من وقتي الشخصي في التصميم؟»** — كل قرار معيب مكلف (ازدواج حجز / FK مكسر للتاريخ / دفع لكل طالب) اتعرّض للمناقشة واتخذ قرار موثق في `01-system-analysis.md`؛ الـ trade-offs مكتوبة صراحةً.
13. **«لو موظف في كلية الهندسة دخل dept وشاف بيانات كلية العلوم، شلون ممنوع؟»** — `users.faculty_id` يقيّد كل استعلام لـ dept عبر join batches→departments→faculty_id؛ الاستعلام على دفعات الهندسة يرجع 403 قبل أي سطر (policy)، والقاعات والمقررات مشتركة بلا فلتر (مسموح — هي للجميع).
14. **«مادة مشتركة بين دبلوم وبكلاريوس — ممكن كل شعبة يدرسها أستاذ مختلف؟»** — نفس المقرر (نفس `course_id`)؛ باثنين سطرين في `timetables` لكل شعبة بمدرّس مختلف؛ شرط بشري: الاثنان في وعاء `course_faculty` للمقرر (UC-21) — وإلا R13 تمنع الحفظ. القاعات والفترات مستقلة لكل سطر.

## 5.5 Checklist نهائية للجنة (يطبعها المشرف)

```
[ ] تسجيل دخول ×4 أدوار (admin جامعة + فلتر كلية / dept مقيد بكليته / guard مركزي يرى كل القاعات / batch دفعته فقط)
[ ] CRUD القاعات/المقررات/الأعضاء/الدفعات + تحقق فريد الحقول
[ ] إعداد جدول برفض سعة + قبول سليم + حفظ
[ ] محاولة تعارض قاعة/مدرس — مرفوضة بأسباب عربية صحيحة
[ ] إعداد امتحان + رفض (امتحان إضافي للشعبة / قاعة مشغولة بمحاضرة) + حفظ + عرض جدول الامتحانات
[ ] عرض شبكة الجدول يتغير مع البرنامج (صباحي/مسائي)
[ ] حجز قاعة + حجز متزامن → 409
[ ] القاعات المتاحة + بحث بالسعة
[ ] الحارس: قفل/فتح + سجل؛ رفض قفل قاعة مشغولة الآن (محاضرة أو امتحان)
[ ] الدفعة: لا ترى غير مساري دفعتها (دبلوم + بكلاريوس) + وسم «جديد»
[ ] التقارير: مخطط + جدول + تصدير CSV
[ ] «ما الحاجات اللي خارج v1؟» — جواب موثق (توليد آلي، push، امتحانات آنلاين/CBT)
```
