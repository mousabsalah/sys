## 0) التصور الصحيح للنطاق (بعد القراءة)

النظام **ليس** مولد جداول آليًا فقط؛ هو نظام إدارة متكامل يشتمل على:

> **حزمة الوثائق للتسليم**: `02-use-cases.md` (حالات الاستخدام + الأدوار) · `03-erd.md` (ERD + القاموس) · `04-dfd.md` (DFD سياقي/مستوى 1/مستوى 2) · `05-demo-scenario.md` (سناريو العرض) · `06-sample-timetables.md` (جداول نموذجية + امتحانات).
> **سلسلة الاعتماد 2026-11-09**: (1) الامتحانات داخل v1؛ (2) الشعب (GROUPS) بدل الدفعة؛ (3) **الهرم التنظيمي جامعة ← كلية ← قسم ← دفعة ← شعبة** — المقررات والقاعات جامعية مشتركة؛ **admin فقط** يعدّل المقررات؛ **guard مركزي** يدير كل القاعات؛ **dept** يرى كليته فقط (faculty-scoping)؛ **admin يرى الجامعة** مع فلتر كلية في اللوحة؛ (4) **وعاء إسناد الأساتذة للمقرر (`course_faculty`)**: لكل مقرر قائمة أساتذة مصادقين؛ اختيار المدرّس في نموذج إعداد الجدول مفلتر بهذا الوعاء؛ وR13 ترفض أي حفظ بمدرّس خارج الوعاء؛ **للمادة المشتركة بين دبلوم وبكلاريوس: سطرا جدول على نفس course_id بأستاذين مختلفين مدعومان**.

1. **إدارة بيانات أساسية**: القاعات / المقررات / أعضاء هيئة التدريس / **البرامج + الدفعات + الشعب (دبلوم/بكلاريوس)** / الفترات لكل برنامج.
2. **إعداد الجدول وعرضه**: ربط مقرر ← مدرس ← **شعبة (GROUPS)** ← قاعة ← زمن، مع **كشف تعارض لحظي** (قاعة محجوزة؟ سعة كافية للشعبة؟ المدرس مش في مكانين؟) وعرض أسبوعي (سبت–خميس × فترات البرنامج).
3. **الامتحانات**: إعداد الامتحان (مقرر/شعبة/تاريخ/من-إلى/النوع) + تحقق تعارض (القاعة عبر امتحانات ومحاضرات + حد امتحانيْن/يوم للشعبة) + عرض جدول الامتحانات + إشعارات تحديثات الامتحان (`EXAM_UPDATES`).
4. **الحجوزات**: حجز يدوي بقاعة/تاريخ/وقت لمقرر أو نشاط + سجل حجوزات اليوم لنفس القاعة + حالة «متاحة/محجوزة/صيانة» لحظية.
5. **الاستعلام عن القاعات المتاحة**: بالوقت والسعة (cards + زر احجز).
6. **لوحة تحكم**: KPIs (القاعات المسجلة، محاضرات الفصل، حجوزات اليوم، قاعات متاحة الآن) + تنبيهات تعارض + آخر الحجوزات.
7. **حرس جامعي**: عرض القاعات الخالية *الآن* (محاضرات وحجوزات **وامتحانات**) وقفل/فتح القاعة مع **سجل قفل مفصل**.
8. **إشعارات الدفعة**: سجل تحديثات (إضافة/تعديل/إلغاء) لشعبتي دفعته (دبلوم + بكلاريوس) — محاضرات وامتحانات؛ "جديد" = بعد آخر دخول للحساب.
9. **التقارير**: نسبة استخدام القاعات (مخطط + جدول) + تصدير.
10. **(اختياري كطور متقدم)**: محرك اقتراح تلقائي للجدول (**Go + Google OR-Tools CP-SAT** — معتمد 2026-11-09) كخدمة منفصلة، وليس في مسار الحفظ اليدوي؛ لا خوارزمية بديلة (GA/SA) في الإنتاج.

الأدوار (بعد اعتماد الهرم؛ من `03-erd.md` §3.3): **admin** (جامعة كاملة + فلتر كلية)، **قسم أكاديمي (dept — فريق الكلية)** (كليته فقط عبر faculty-scoping؛ المقررات للقراءة فقط يعدلها admin فقط)، **حرس جامعي (guard — مركزي)** (كل قاعات الجامعة + سجل كامل، لا تعديل جداول)، **دفعة** (جدول وامتحانات دفعتها فقط — دبلوم وبكلاريوس).

> ⚠️ تصحيح لماسبق: `docs/00-problem-formulation.md` كان مبنيًا على فهم «مولد جداول آلي» فقط؛ هذه الوثيقة تحل محلها كتعريف للنطاق. الـ optimization يظل **وحدة قابلة للتفعيل داخل النظام** لا أساس النظام.

## 1) الداتا فلو (DFD)

### 1.1 المخطط السياقي (Context — Level 0)

```text
                 بيانات أساسية (قاعات/مقررات/أعضاء/دفعات)
        ┌───────────────────────────────────────────────┐
        │                                               ▼
  مدير النظام ───────────────┐                ┌─────────────────┐
  قسم أكاديمي ──────────────┤                │                 │
                             ├──►  نظام      │  توليد جداول/    │
  حرس جامعي ── عرض الآن/قفل/فتح ─►  إدارة     │  حجز القاعات   │
                             │    القاعات    │  وكشف التعارض   │
  دفعة ──────── عرض فقط ──────┴──► والجداول ───┴──┬──────────────┘
                                                   │
        ┌──────────────────────────────────────────┘
        ▼
  مخرجات: الجداول، إشعارات الدفعة، سجل القفل، تقارير الاستخدام
```

الكيانات الخارجية: `مدير النظام`، `قسم أكاديمي`، `حرس جامعي`، `دفعة`. لا يوجد كيان خارجي ثالث (الطباعة/التصدير = مخرج داخل النظام).

### 1.3 Level 2 — P2 (كشف التعارض) مثال تفصيلي

```text
المدخل: {المقرر c، العضو p، الدفعة s، القاعة r، اليوم d، من t1 ← إلى t2}

P2.1 تحقق القاعة   ← D5,D6: r مستخدمة في (d, تداخل زني [t1,t2])؟ أي حجز/محاضرة نشطة؟
P2.2 تحقق المدرس   ← D5: p لديه محاضرة في نفس (d, [t1,t2])؟
P2.3 تحقق الدفعة   ← D5,D6: s لديها محاضرة/حجز في (d, [t1,t2])؟ (حظر تزامن مجموعتين)
P2.4 تحقق السعة    ← D1.cap ≥ D4.عدد_طلاب؟ (40 ≥ 55 ⇒ رفض: «السعة غير كافية»)
P2.5 تحقق التجهيزات← D1.التجهيزات ⊇ D2.متطلبات المقرر؟ (إن وُجدت متطلبات)
P2.6 تحقق الحالة   ← D1.حالة = «متاحة» (صيانة/مغلقة ⇒ رفض)
P2.7 تحقق القفل    ← D8 آخر إجراء للقاعة r؟ «قفل الآن» ⇒ رفض الحجز/الإضافة

النتيجة: مقبول ← كتابة D5 (+D9 إشعار)  |  مرفوض ← رجوع بقوائم أسباب (حسب الكروكي photo_1:
«القاعة: تعارض، محجوزة في هذا الوقت»، «السعة: [40] أقل من عدد الطلاب [55]»، «عضو هيئة التدريس: لا تعارض ✓»)
```

### 1.4 تدفقات الحراس والإشعارات (خصوصية النظام)

- **قفل قاعة**: P4 يقرأ D5,D6 (الآن: أي محاضرة/حجز قائم الآن؟) ⇒ إن لا، اكتب D8(قاعة، حارس، قفل، وقت) والقاعة تصبح «مغلقة مؤقتاً» في الحسابات ذات الدور الحارس فقط؛ الفتح عكسي. **القفل لا يمنع Γ التعديل من مدير النظام** (مدير يرفع القفل بالضرورة أو يلغه صراحةً حسب سياستك).
- **التحديث للدفعة**: أي كتابة/تعديل/إلغاء في D5 للدفعة s ⇒ اكتب D9(رقم الدفعة، رقم الجدول، النوع، الوصف، وقت). واجهة الدفعة تعرض «جديد» مقابل آخرُ تسجيل دخول. **لا** تُرسل إشعارات push في v1 — العرض عند الدخول فقط (يوفي بـ«الفرع المخفي» في التحليل).

## 2) التصور العام (البنية)

### 2.1 التقنية المعتمدة في فصولك (التزامًا بنصك)

| الطبقة | التقنية | دورها |
|---|---|---|
| Frontend | **React** (+ Bootstrap للسرعة، RTL) | الشاشات الـ8: تسجيل دخول، لوحة، بيانات أساسية، جداول (عرض/إعداد)، حجز، قاعات متاحة، تقارير — `dir="rtl"` |
| Backend | **Laravel (PHP 12+)** + Eloquent + FormRequests | REST API، منطق الأعمال، RBAC (middleware)، transactions |
| DB | **MySQL** (ACID) | التسعة كينونات → جداول بـ FK + indexes |
| محرك الاقتراح (طور متقدم) | **Go** + **OR-Tools CP-SAT** (معتمد 2026-11-09) | توليد جدول مقترح عبر CP-SAT؛ يُستدعى يدويًا، لا يؤثر في مسار الحفظ؛ نفس النهج للمحاضرات والامتحانات (graph coloring كمفاهيم نظرية للامتحانات فقط — لا خوارزمية إنتاج) |
| أدوات رديفة | Python (تحليل استغلال القاعات/تقارير بحثية) | اختياري، لا يدخل مسار الإنتاج |
| التقارير | مكتبة PHP (mPDF أو Dompdf) + تصدير CSV | طباعة الجداول + تصدير Excel |

> Go ليس بديلًا عن Laravel؛ Laravel هو العمود الفقري (CRUD + تفويض + معاملات)، وGo «مستشار تحسين» يستدعيه زر «اقتراح جدول» ويعيد مسودة يعرضها المستخدم للمراجعة ثم يعتمدها يدويًا. هذا يحترم نص فصلك («تُسند إلى Go عملية تنفيذ محرك الجدولة التلقائي…») دون تحميل كل حفظ بمعالجة Go.

### 2.2 المعمارية (Layers + Modules)

```text
┌──────────────────────────────────────────────┐
│ React SPA (RTL)                               │
│  - pages/ (login, dashboard, master-data,      │
│    timetables, bookings, guard, reports)       │
│  - api/ (client + types) — لا DOM logic فيها   │
└───────────────────────┬────────────────────────┘
                        │ HTTPS/JSON (Laravel Sanctum أو session cookie)
┌───────────────────────▼────────────────────────┐
│ Laravel API (Modular Monolith)                  │
│  routes/api.php → Controllers (thin)            │
│  → FormRequests (validation) → Services         │
│     (CheckerClient→Go service)                  │
│      BookingService, LockService, ReportService,│
│      Notifier)                                  │
│  → Models (Eloquent) + Policies/RBAC            │
│  ↔ MySQL (transactions + FOR UPDATE)            │
│  → Go `syst-engine` (المهام الحسابية)            │
└──────────────────────────────────────────────────┘
```

النمط: **Modular Monolith** أولًا (قرار واعي): خدمة واحدة تُنشر بسهولة لمناقشة تخرج، مع حدود وحدات صارمة تتيح سحب أي وحدة لاحقًا إن لزم (Microservices ذكرها فصلك لكنها overkill لمشروع تخرج). «Client-Server» هو النمط المعماري كما صنّفته في 2-2-3.

### 2.3 قواعد البيانات (17 كيانًا، FK صريحة)

`faculties`, `departments`, `programs`, `periods`, `halls`, `courses`, `course_faculty`, `faculty`, `batches`, `groups`, `timetables`, `bookings`, `users`, `guard_locks`, `timetable_updates`, `exam_sessions`, `exam_updates`.
مفاتيح: `departments → faculties`؛ `batches → departments` و`groups`؛ `course_faculty → courses/faculty` (وعاء أهلية؛ `UNIQUE(course_id, faculty_id)`)؛ `timetables/bookings` → halls/courses/faculty (+`groups` للجدولة؛ `timetables.faculty_id ∈ وعاء course_faculty` شرط R13)؛ `groups → batches` و`timetable_updates`/`exam_updates → groups`؛ `guard_locks` → halls, users؛ **halls/courses بلا faculty_id (جامعية مشتركة)**.
قيود DB: `UNIQUE(name)` للقاعات، `UNIQUE(code)` للمقررات، `UNIQUE(username)` للمستخدمين، `UNIQUE(email)` للأعضاء، `UNIQUE(batch_id, track)` للشعب، `UNIQUE(faculty_id, name)` للأقسام، CHECKs على الأوقات + `groups.track ∈ {دبلوم,بكلاريوس}` + `groups.student_count > 0` + `users.faculty_id IS NOT NULL ⇔ role='dept'`، فهارس على `(hall_id, day|date|exam_date)` و`timetables(group_id, day_of_week)` للتقارير وكشف التعارض.

### 2.4 الأمان والصلاحيات (RBAC — 4 أدوار)

كل مسار API محروس بـ middleware `role:admin|dept|guard|batch`:
- admin: كل شيء (بما فيه إدارة الحسابات).
- dept: **كليته فقط** (faculty-scoping عبر `faculty_id` للمستخدم): CRUD دفعات/الشعب/الأعضاء لكليتها + timetables/bookings/exam_sessions لكليته — **المقررات للقراءة فقط** (يعدلها admin فقط)؛ لا قاعات، لا قفل، لا حسابات.
- guard **مركزي**: `GET /status/now` (كل القاعات) + `POST /halls/{id}/lock|unlock` (أي قاعة) + `GET /locks` — لا كلية ولا تعديل إطلاقًا.
- batch: `GET /batches/me/timetable` + `GET /batches/me/exams` + `GET /batches/me/updates` (read-only عبر Policy؛ يرى مساري دفعته).
- admin: كل الجامعة؛ اللوحة تعطي فلتر كلية اختياري؛ يرى الكل بلا حدود.
كلمات المرور `Hash::make` (bcrypt)؛ لا mass assignment خارج fillable؛ rate-limit لتسجيل الدخول؛ سجل عمليات حسّاسة في `guard_locks`/`timetable_updates` (لا تُحذف، تُلغى بحالتها).

## 3) طريقة التنفيذ (خطة مراحل — مع SDLC من فصلك)

المرحلة 0 — **تثبيت القرارات** (جلسة واحدة مع المشرف): تأكيد الستاك (Laravel+React+MySQL+Go-engine كطور أخير)، نطاق v1 = الشاشات الـ8 + **وحدة الامتحانات (P8)** مع تمييز الشعب (دبلوم/بكلاريوس) — تم الاعتماد؛ لم يُعتمد محرك Go «اقتراح» (يُؤجل).

المرحلة 1 — **النمذجة**: استكمال Use Cases (21 حالة: تسجيل دخول، CRUD ×6 (شامل إسناد الأساتذة UC-21)، إعداد جدول+تحقق، عرض جدول، حجز، قاعات متاحة، قفل/فتح، تحديثات دفعة، تقارير، **إعداد امتحان+تحقق، عرض امتحانات، تحديثات امتحانات، إدارة الكليات والأقسام**)، ERD بـ 17 كيانًا، DFD Level 1/2 (هذه الوثيقة)، API contract (OpenAPI مبدئي)، مخطط جداول MySQL + migrations.

المرحلة 2 — **النواة الخلفية**: Laravel skeleton + migrations + seeders (**جامعة وهمية واقعية: 3 كليات / 4–6 أقسام / 4 برامج / 8 دفعات / 6–16 شعبًا حسب المسارات / 60 قاعة / 220 مقررًا مشتركة / 25 عضوًا**) + Models + RBAC (middleware + policies + `faculty_id` scope على dept) + CRUD الـ6 (بما فيها الكليات/الأقسام/الشعب).

المرحلة 3 — **الجداول + التعارض**: خدمة **Go `syst-engine`** (HTTP/JSON على localhost) هي مسار التحقق الوحيد — `POST /check {type:lecture|exam|booking, ...}` يرجع تقرير أسباب JSON؛ Laravel لا يقرر تعارضًا بنفسه — تنسيق + transaction + RBAC + payload/verdict فقط + endpoints: `POST /timetables/check` (proxy)، `POST /timetables` (transaction: check → **R13** → insert → insert timetable_updates للشعبة) + `GET /timetables?by=group|faculty|hall&id=` للشبكة الأسبوعية؛ وقائمة المدرّسين في نموذج الإعداد **مفلترة حسب المقرر** (عبر D14).

المرحلة 3.5 — **الامتحانات**: `ExamService` (نفس سلسلة P2 بحقل `type=exam` + R7 التقاطع محاضرة↔امتحان في نفس القاعة/الفترة + R8 حد امتحانيْن/اليوم للشعبة) + endpoints: `POST /exams/check`، `POST /exams`، `GET /exams?by=group|course&id=` + واجهة عرض/إعداد (كروكي مشابه لـ photo_1).

المرحلة 4 — **الحجوزات + الحارس**: `POST /bookings/check-availability`، `POST /bookings`، `GET /halls/available?date&from&to&min_capacity`، `PATCH /halls/{id}/lock|unlock` (يُرفض إن وُجد timetable/booking/**exam** سارٍ الآن) + `GET /status/now` للحارس.

المرحلة 5 — **اللوحة والتقارير**: KPIs endpoint واحد `GET /dashboard` (4 أرقام + آخر 5 حجوزات + تنبيهات تعارض = استعلام detection عن ازدواج حالات سابقة/مفترضة) + تقرير الاستخدام `GET /reports/utilization?from&to` (عدد المحاضرات لكل قاعة ÷ السعات المتاحة الزمنية ⇒ نسبة) + تصدير CSV (+ PDF إن اتسع الوقت).

المرحلة 6 — **واجهة React (RTL)**: الشاشات الـ8 + **شاشتا الامتحانات** (إعداد + عرض جدول الامتحانات) مطابقة للكروكيات (نفس التخطيط: sidebar بالأسود الظاهر للقسم النشط)، مع `api/` client موحد، نماذج بـ controlled inputs، شاشة تحقق التعارض تعرض أسبابًا بالعربية كما في الكروكي، جدول أسبوعي CSS Grid، حالات تحميل/خطأ/فارغ لكل شاشة.

المرحلة 7 — **محرك CP-SAT (اختياري/تخرج «feature»)**: خدمة HTTP بسيطة في نفس Go `syst-engine` تستقبل JSON (مقررات، أعضاء، شعب، قاعات، تفضيلات) وتُعيد مسودة جدول بمعنى «مقترح» عبر **Google OR-Tools CP-SAT**؛ الزر في الواجهة: «اقتراح تلقائي» ← عرض النتيجة للمراجعة ← «اعتماد» يمر بنفس مسار P2 (check → save + updates). **لا يُغيّر شيئًا في مسار الحفظ اليدوي**، وفشل Go لا يُسقط النظام.

المرحلة 8 — **التشطيب**: UAT على بيانات جامعة حقيقية (إن توفرت) أو وهمية كبيرة (20 قاعة × 60 مقرر)، اختبار race على الحجز المتزامن، توثيق التشغيل، وتسليم فصول 4–5.

**إستراتيجية التحويل** (من فصلك): «تحويل قيادي تجريبي» على قسم أكاديمي واحد لترم واحد ثم تعميم — يناسب الجامعة ويقلل المقاومة.

## 4) العزل وجودة الكود — قواعد ملزمة

### 4.1 العزل (Separation of Concerns)
- **الطبقات**: Controller → FormRequest → Service (منطق) → Model. الـController ≤ 15 سطرًا؛ لا SQL في Controller ولا قرار تعارض فيه.
- **الوحدات**: `App\Modules\{Identity,MasterData(هيكل+قاعات+مقررات+أعضاء+دفعات+شعب),Timetable,Booking,GuardLock,Reporting,Notifications,Exams}`؛ كل وحدة: Models/Services/Requests/Controllers خاصة؛ لا استيراد نموذج من وحدة أخرى مباشرة — تواصل عبر Services فقط.
- **الخدمة النقية**: التحقق يعيش في **Go `syst-engine`** (بالزخرفة التي تختزن كل الدوال النقية: `check.go` لكل type) — Go بلا I/O على طلباتك: تستقبل payload كامل من Laravel وترد بأسباب JSON (`{code, message_ar, severity}`)؛ القرار يتخذ في Go؛ Laravel لا يكرر منطق التعارض أبدًا (طريق واحد فقط). عازلته في Laravel: `CheckerClient` interface + تطبيقان: `GoChecker` (HTTP) للإنتاج و`FakeChecker` (in-memory ثابت) للاختبارات.
- **عزل Go**: `SchedulerClient` interface بـ `propose(Request): ?Draft`؛ تطبيقان: `FakeSchedulerClient` (للاختبارات: يرجع مسودة ثابتة) و`GoSchedulerClient` (HTTP). عند فشل Go: يعرض الـ UI «تعذر الاقتراح — تابع يدويًا».
- **الواجهة**: `api/client.ts` (axios + interceptor للأخطاء)؛ الشاشات لا تعرف fetch/axios؛ الحقول العربية عبر `lang/ar.json` لا hardcoded (حتى لو لغة واحدة الآن).

### 4.2 الذرّية والتزامن (هنا يُكسر النظام عادةً)
- الحجز/الحفظ داخل `DB::transaction()` مع `SELECT ... FOR UPDATE` على سطر القاعة (يمنع حجزين متزامنين لنفس الفترة) + إعادة طلب `/check` داخل المعاملة (TOCTOU). الحفظ والامتحان يشتركان في القفل — **لا يوجد قفل منفصل للامتحانات** (نفس القاعة).
- فريد منطقي `(hall_id, date, start_time, end_time)` لا يُطبَّق بـ unique index وحده (التداخل ≠ تساوي) ⇒ الاعتماد على transaction + locking، والـ unique index للحالات المتطابقة تمامًا فقط.
- مؤشرات: `timetables(hall_id, day)`، `bookings(hall_id, date)`، `exam_sessions(hall_id, exam_date)` و`exam_sessions(group_id, exam_date)` — تجعل كشف التعارض O(log n).
- Idempotency: `POST /bookings` يقبل `Idempotency-Key` (UUID من الواجهة) ويُخزّنه — إعادة النقر لا تُنشئ حجزين.

### 4.3 سلامة البيانات والجودة
- **Laravel Pint** (format) + **PHPStan/Larastan مستوى 6+** في CI حتى يدويًا قبل التسليم؛ `declare(strict_types=1)`.
- Enums بدل strings: `HallStatus`, `HallType`, `Role`, `BookingStatus`, `UpdateType`, `Track`, `ExamType`.
- DTO ثابتة (`readonly class`) لنواتج التحقق: `ConflictReport` (أسباب مرقمة + أصناف hard/soft).
- الفهارس والقيود على مستوى MySQL (وليس التطبيق فقط) — آخر خط دفاع.
- `softDeletes` للقاعات/المقررات (لا فقدان سجل تاريخي للجداول).

### 4.4 الاختبارات (الحد الأدنى المقنع للمشرف)
- Unit (Go `syst-engine`): جدول تعارض كامل — قاعة/شعبة/مدرّس/سعة/أهلية R13/R7 (محاضرة↔امتحان)/R8 (امتحانيْن للشعبة/اليوم) + حالة نظيفة + متاخمة الفترات (08:00–10:00 ↔ 10:00–12:00).
- Feature (Laravel): حجز مزدوج متزامن (two HTTP requests متوازيتان) ⇒ واحد 200 وآخر 409؛ سعة 40 مقابل شعبة بكلاريوس 55 ⇒ 422 مع الرسالة الصحيحة؛ الحارس ممنوع من POST timetables/exams (403)؛ دفعة لا ترى امتحانات أخرى (403/404)؛ **dept لا ترى دفعات خارج كليته (403)**؛ **guard يرى قاعات كل الكليات**.
- Seed بيانات جامعة وهمية كبيرة لاختبار الأداء (< 100ms? لطلب `/check`).
- Go هو مسار v1: لا تؤجل اختباراته لـ «مرحلة مستقبلية».

### 4.5 الجودة الشكلية (للتخرج)

- عدّاد "technical debt" صريح في نهاية README: (1) لا إشعارات push، (2) محرك Go اختياري، (3) لا نسخ احتياطي تلقائي — مع ذكر الحل لكلٍّ لاحقًا.
